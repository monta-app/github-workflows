## Recent Changes (2026-10-27)
1. **`reviewer-package.yml`**: posts one PR comment with the context a reviewer can't get from the diff: PRs in other repositories with the same Jira key (title or branch) or linked from the description, earlier PRs that changed the same files (from squash-merge subjects on the base branch via the commits API, so no checkout), and an optional Claude overview with a Mermaid `flowchart` and a review order. GitHub search splits a key like `ABC-123` into words and returned unrelated PRs, so hits must contain the whole key in their title or body. Cross-repo search needs `ORG_READ_TOKEN`; `GITHUB_TOKEN` only sees the calling repository. That token can read repositories the comment's readers can't, so a public caller drops private-repo hits, and the docs ask for a read-only token scoped to repositories every reader may see. A job-level `concurrency` group stops two quick triggers from posting two comments. The overview also gets each related PR's description, files and diff (6 PRs, 30k characters of diff each, other repositories first) so it can explain how they connect, the merge order, and contract mismatches between the two sides; the diagram groups nodes by app, service or repository (`flowchart TD`), as one long `flowchart LR` line was too small to read. The Claude step is `continue-on-error` and the comment ships without the overview when it fails. Tried locally against internal PRs (comment body only, nothing posted).

## Recent Changes (2026-10-23)
1. **`pnpm-dependency-submission.yml` and the `pnpm-dependency-graph` action**: pnpm 12 writes `pnpm-lock.yaml` as two YAML documents (one pinning pnpm itself via `packageManagerDependencies`, then the workspace lockfile), and GitHub's dependency graph reads only the first, so it falls back to each workspace's `package.json`. The SBOM then has only direct dependencies with their specifiers. monorepo-typescript listed 906 packages, 895 as `catalog:…`, against the 2,795 its lockfile resolves. The action reads every document with `yq` (no install), walks each importer's dependencies through `snapshots`, and submits one manifest per workspace named `<importer>/package.json`. Tested on tool-reviews: a single `pnpm-lock.yaml` manifest left GitHub's 30 `package.json` specifiers next to the resolved versions, while manifests named after the `package.json` files replaced them (540 entries, 430 unique packages, all with a license, no specifiers). Scope follows npm: anything a workspace's `dependencies`/`optionalDependencies` reach is `runtime`, the rest `development`. Edges to a package's `peerDependencies` (pnpm lists resolved peers, optional ones included, under the snapshot's dependencies) don't decide a scope, which kept vitest and `@types/react` from turning runtime through `@testing-library/jest-dom` and `posthog-js`; a package reachable only through a peer takes the scope of what reaches it. Workspace-level scoping (a config package linked only as a devDependency) was tried and dropped: the lockfile can't tell such a package from an app that a dev tool links to (`apps/storybook` dev-links `apps/hub`). Unittests: `python3 .github/actions/pnpm-dependency-graph/test_pnpm_dependency_graph.py`.
1. **`GHL_USERNAME`/`GHL_PASSWORD` optional on `gradle-dependency-submission.yml`**: only builds that resolve packages from GitHub Packages need them, and the Kotlin repos with their own CI that are next to call the workflow include public libraries and tools that don't. A required secret the caller can't see would leave those repos unable to call it. `sonar-cloud.yml` still requires them for its own build and passes them on.
1. **Fixed job correlator for dependency submission**: `gradle-dependency-submission.yml` sets `GITHUB_DEPENDENCY_GRAPH_JOB_CORRELATOR: gradle-dependency-submission` (the action only derives one from the workflow and job when it is unset), so every repo's snapshot and artifact are named alike: `dependency-graph_gradle-dependency-submission.json`. Before, the name followed the calling workflow (`code_analysis-submit`, `main_branch_workflow-submit`), so a reader had to list all of a repo's artifacts to find it, and in a repo that keeps many artifacts (service-ocpi, about 20 per run) GitHub's unfiltered `GET /repos/{repo}/actions/artifacts` returns 500 even at `per_page=5`, while `?name=` answers in under a second. GitHub keeps the last snapshot of each correlator, so each repo that submitted under an earlier name still has that snapshot next to the new one; it is no longer updated.
1. **`gradle-dependency-submission.yml`**: the dependency submission from `sonar-cloud.yml` is now a reusable workflow of its own, for two reasons. Inside the Sonar job it ran after the tests, so a repo whose tests fail or run past the job's 30-minute timeout never submitted (service-energy-meter, service-control and service-cdr-revenue-reconciliation were stuck that way), and repos that don't use `sonar-cloud.yml` (service-ocpi, service-charges, the Kotlin libraries) had no way to submit. The workflow restores the Gradle cache (restore only; the build jobs save it), resolves every configuration with `gradle/actions/dependency-submission` without compiling or testing, strips the proxy `repository_url` qualifier as before and POSTs the snapshot. It only runs on the default branch (the `setup` job's `if`, so the rest is skipped elsewhere). It doesn't declare `permissions:`: a nested job asking for `contents: write` when the caller grants less fails the whole workflow at startup, while an undeclared one just gets a failed submit step. `best-effort` (default `false`) makes the two steps `continue-on-error`; a job calling a reusable workflow can't set `continue-on-error`, so this is how `sonar-cloud.yml` keeps its "never fails" promise. `sonar-cloud.yml`'s `submit-dependencies` now adds a `dependencies` job calling it (`best-effort: true`) in parallel with the tests, and the inline steps are gone. The artifact name changes with the job (`dependency-graph_*` still); readers should match the prefix.

## Recent Changes (2026-10-22)
1. **Dependency submission matches packages to Maven Central**: the Gradle plugin adds a `repository_url` purl qualifier to every package not resolved from Maven Central itself, and on ARC everything resolves through the CodeArtifact proxy, so the first opted-in repo (service-wallet) submitted 1,037 packages of which only `org.gradle:gradle-core` (no qualifier) got a license in GitHub's SBOM export; GitHub treats a qualified package as coming from that other repository and has no license or advisory data for it. The plugin has no switch for the qualifier, so the step now generates the graph with `dependency-graph: generate-and-upload` (the artifact is unchanged), then a `Submit Gradle dependency graph` step strips `?repository_url=…` with `jq` from every package except GitHub Packages ones (`maven.pkg.github.com`, kept so first-party libraries stay distinguishable) and POSTs the snapshot to `/repos/{repo}/dependency-graph/snapshots` with the job token. A package from a non-Central repository loses only a label GitHub can't use. Checked on service-wallet's real graph: 1,027 packages lose the qualifier, the 10 `com.monta.*` ones keep it, scopes and the snapshot fields are unchanged. Both steps stay `continue-on-error`; the submit step only runs when generating succeeded. `jq` and `curl` come from the runner image.
1. **`submit-dependencies` on `sonar-cloud.yml`**: when set, a run on the default branch runs `gradle/actions/dependency-submission` (v6.4.0, pinned) after the tests, so the Gradle dependencies the build resolves reach GitHub's dependency graph. GitHub's dependency graph has no Gradle support from manifests, so without this a Kotlin repo's Dependabot alerts and its SBOM export (`GET /repos/{owner}/{repo}/dependency-graph/sbom`) list no Gradle packages, which leaves license scanning blind to them. It runs after the tests so the dependencies are already in the Gradle cache, gets `GHL_USERNAME`/`GHL_PASSWORD` like the build steps (GitHub Packages; CodeArtifact comes from the runner image's init script), and uses `cache-provider: external` because the job restores and saves the Gradle cache itself (the action's default `enhanced` cache is a commercial service). Only the default branch's submission is shown by GitHub, so other refs skip the step. It's `continue-on-error`. Submitting needs `contents: write`; the step relies on the repository's default workflow token rather than declaring `permissions:`, because a nested job asking for more than its caller grants fails at startup, which would break Code Analysis in repos whose default token is read-only (there the step just fails softly). `DEPENDENCY_GRAPH_RUNTIME_EXCLUDE_CONFIGURATIONS` is set from `dependency-development-configurations` (tests and build tooling by default), which turns on scopes: dependencies resolved only there are `development`, any also resolved elsewhere `runtime`. GitHub keeps the scope for Dependabot but its SBOM export drops it, so the graph is also saved as a workflow artifact (the action's default `generate-submit-and-upload`, 30 days) for tools that need it. Off by default; repos opt in one by one.

## Recent Changes (2026-10-13)
1. **`argocd-resource-name` on the v2 deploy workflows**: `deploy-generic-v2.yml` and `deploy-kotlin-v2.yml` accept `argocd-resource-name` and pass it through `component-deploy-v2.yml` to `argocd-wait-sync`'s existing `resource-name` (kind stays `Deployment`). The wait then requires the expected revision, `Synced`, and that Deployment healthy, and ignores the app's aggregate health. Without it, any Degraded resource in the app fails the deploy on the first poll: service-monta-factory run 38388140776 failed with its Deployment `Healthy` because a CronJob's last Job had failed. Empty (the default) keeps tracking the whole app.
1. **`arc-job-report` reads `mimir-internal` at 15 s**: ARC's cAdvisor and kube-state-metrics series stopped arriving in `grafanacloud-prom` around 2026-10-01, so every job came back `no metrics` and no runner was ever suggested. `job_resources.py` queries `mimir-internal` (uid `ffzoywkuhm5tsd`) at a 15 s step with `rate[1m]`; the old 60 s / `rate[2m]` reported 2-minute averages and hid CPU bursts (monorepo Lint p90 peak 1.8 → 3.3 cores).
1. **`arc-job-report` sizes runners from the job's last 7 days**: one run is not safe to size on, because cache hits change a job's peak memory a lot (monorepo Typecheck: 1.5 GB typical, 13.1 GB worst). The history comes from the `arc:job_memory_working_set_bytes:max1m` and `arc:job_cpu_usage_cores:rate1m` recording rules in monta-app/terraform, which join each runner pod to its GitHub job (`repository`, `job_name`, `workflow_run_id`) once a minute. Doing that join at read time over 7 days OOM-killed the mimir-internal query-frontends, so the report must only read the recorded series. Runners have a memory limit but only a CPU request, so memory is a hard floor (1.3 × the 7-day peak; an OOM kill always moves up a size) and CPU is a labelled trade-off: ⬆️ *CPU-bound, faster* when the median is ≥ 85% of the runner's vCPU; a smaller size must cover the median and is *fits* or *trial: may be slower* depending on the peak. Smaller sizes need 5 runs in the window; there is no backfill, so they start a week after the rules are applied. The old 2-minute cut-off is gone, since the history covers short jobs. The local path uses `gcx api` against the same datasource-proxy URL as CI, because `gcx metrics query` silently widens the step to about 100 points.
1. **`arc-job-report` groups `(shard N)` and `(shard-N)` shards**: shards were only recognised as `<name> - shard N` (service-ocpi; server uses `unit-tests (shard-N)`), and `name()` strips a `(…)` suffix before that check, so monorepo-typescript's `Test (shard N)` jobs collapsed into one jobs-table row together with the separate `Test` gate job (linking only the slowest shard), and got one suggestion row each ("💡 11 runner changes", 7 of them identical Test rows). Both formats now group into a `Test · shards 1 2 …` row in both tables; in the suggestion table shards are grouped per change and reason, showing the highest memory and CPU and the fewest runs, and the 💡 count is the number of rows. Jobs that aren't shards are grouped by their full name, so two jobs differing only in a `(…)` suffix keep separate rows.
1. **`arc-job-report` keeps one comment per PR with a section per workflow**: monta-app/server runs its ARC jobs in several workflows (`Unit tests`, `Integration tests`, `Static checks`, `Smoke tests`), and with a single section each workflow's run would have overwritten the others' table and mixed their run histories. Each section starts with `<!-- workflow: <name> -->`; a run re-renders only its own, and the 50-run history is split evenly between sections to stay under GitHub's comment limit. A comment from before sections is adopted as the reporting workflow's section, history included. A run whose commit has no PR now prints a message and exits 0 instead of failing, since push-triggered workflows on a branch without a PR are normal (monorepo-typescript had a red run from it).

## Recent Changes (2026-10-07)
1. **Terraform plans are stored beside the state, not as Actions artifacts**: `terraform-stack.yml` writes the saved plan to `s3://<bucket>/tfplans/<state key>/<pr head sha>.tfplan`, read from the initialised backend in `.terraform/terraform.tfstate`, and the apply downloads and then deletes it. A saved plan is a zip of the full prior state (`tfstate`, `tfstate-prev`) plus every variable value, `sensitive` or not, and Actions artifacts are downloadable by anyone with read access to the repository — the whole org. Verified locally: a `sensitive` data-source value was absent from the text plan and present in `terraform show -json tfplan`. The shared `tfplans/` prefix is what lets one bucket lifecycle rule expire unapplied plans and the noncurrent versions left by the post-apply delete (S3 lifecycle filters only match a literal key prefix); the cost is that roles scoped to their own state prefix need `tfplans/<prefix>/*` added. Stacks must use the `s3` backend; anything else fails with `Unsupported backend`. `plan-retention-days` and the `Slug the stack path` step are gone, and callers no longer need `actions: write`. The runner needs the AWS CLI. Callers pinned to an older SHA keep uploading artifacts until they bump, and a PR planned under the old pin finds no plan after the bump, so it needs a fresh plan or a `recover`.

Before, the changed-file list only chose which files to scan, and each one was scanned in full, so touching a file with an old finding failed the PR (service-api-gateways#4615 went red on a `secrets: inherit` already on main). The merge base is computed before `set +e`, so if it fails the step goes red. Inline, it would pass an empty sha, Semgrep would error, and the step's fallback would report zero findings. Trade-off: old findings in touched files no longer show on PRs.

## Recent Changes (2026-09-11)
1. **`check-migration-order` action + wired into `pull-request-kotlin.yml`**: New composite action at `.github/actions/check-migration-order` that fails a PR adding a Flyway migration whose version sorts before one already applied on the base branch, misnaming a new migration, or editing/renaming/deleting a committed one. Comparison is against the base branch **tip**, not `git merge-base` — the merge base cannot contain migrations that landed after the branch was cut, which is why merge-base checks miss the failure entirely (it stalled service-charges staging for a day, CPONETOPS-1355). Deliberately a composite action and NOT a reusable workflow: a reusable workflow's status check is named `<caller job>/<inner job>`, which would rename service-ocpi's required `Check Migration File Naming` check and force a branch-protection change. `migration-paths` defaults to empty = auto-discover every directory named `migration` under `src/main/resources` holding a `.sql`, unioned from the working tree and the base branch; each root is an independent Flyway version namespace. The root is the `migration` dir itself, NOT each dir containing a `.sql` — Flyway pools `common/`, `<env>/`, `stored/procedures/` into one namespace, so splitting them would let an out-of-order migration pass (service-charges: `common` at 2026 vs `stored/procedures` at 2021). Versions compare with `sort -V`, since real filenames break lexicographic order (`V2025.08.05.8.51`, `V2026.02.04.1400`). Added as a `check-migration-order` job in `pull-request-kotlin.yml`, so every Kotlin caller gets it with no per-repo config; repos with no migrations pass trivially. Verified across 19 Kotlin checkouts (1 root for most, 2 for ocpp/energy/wallet/api-gateways/control, 0 for vehicle/cpi-api).

## Recent Changes (2026-08-28)
1. **`argocd-wait-sync` resource-level tracking**: Added opt-in `resource-name` (+ `resource-kind`, default `Deployment`, and `resource-namespace`) inputs to `.github/actions/argocd-wait-sync`. When `resource-name` is set, completion and fail-fast (Degraded/Missing) are judged on that specific resource in `.status.resources[]` instead of the app's aggregate `.status.health`, so an app that manages multiple independently-owned resources (e.g. a shared/monorepo-style app with several Deployments) won't falsely pass before your resource rolls out, or block forever because an unrelated resource in the same app is Degraded/Progressing. Empty `resource-name` (default) is fully backwards compatible - identical behavior to before. `wait-sync.sh` gains a `TARGET_HEALTHY` variable that is the single source of truth for "is the thing we care about healthy" (the tracked resource when set, otherwise app aggregate health), used by both phases of the state machine. `test-local.sh` gains matching `--resource-name`/`--resource-kind`/`--resource-namespace` flags.
